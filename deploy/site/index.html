Small models, small windows, still on task.

ContextGC is a proxy between an AI agent and Ollama. Before every model call it cleans the agent's history: duplicates go, huge tool outputs move to disk behind a pointer, and old low-value turns are evicted only under pressure. The agent needs no code changes, only a new URL.

The problem, and what ContextGC does

Agents resend everything

Every step sends the whole history again: file reads, logs, test output. It grows past the model's context window within a few steps.

Ollama cuts silently

When the prompt is too long, the oldest messages are dropped without warning. The oldest message is the task itself, so the agent forgets what it was asked to do.

ContextGC cleans first

It keeps the task and recent work, moves bulky tool output behind a short pointer, and drops old filler, so the prompt fits and nothing important is cut.

Which parts of ContextGC matter

Each variant switches off exactly one stage of the pipeline and reruns every task. A big drop means that stage is doing real work.

CrewAI, a real agent framework

Two CrewAI crews (incident response, code maintenance) on a demo repository with a 2,000-line outage log. CrewAI 1.15 has its own context handling: it parks large tool results in files. We ran it both with that feature on and with it off, each against raw Ollama and through ContextGC.

How to read these numbers

  • Same model, prompt, tools, temperature 0 and seed in every lane. Only the context handling differs.
  • Even at temperature 0, identical runs on a GPU can end differently. Treat gaps of one or two runs as noise.
  • The 8 tasks are small Python repair jobs we wrote, with earlier-session noise added to the history. Results on other workloads may differ.
  • "Raw, big window" never ran out of room here, so it is what running the model normally looks like.
